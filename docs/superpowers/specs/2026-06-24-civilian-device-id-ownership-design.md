# Design: Restore Civilian `device_id` Ownership After PR #448 Encryption

**Date:** 2026-06-24
**Status:** Design (v1)
**Closes:** Bug surfaced by handoff — submitter cannot track/append/followup/notify on their own report
**Supersedes:** N/A (no prior design for this fix; PR #448 design did not cover the post-encrypt ownership path)

---

## Problem

PR #448 (`feat(#429): encrypt witness PII and AI narratives at rest`, merged 2026-06-23, commit `c22591a5`) extended AES-256-GCM at-rest encryption to four `wims.citizen_reports` columns: `witness_name`, `witness_phone`, `device_id`, `ip_hash`. As part of that change, the post-INSERT call to `_encrypt_witness_pii()` (`src/backend/api/routes/civilian.py:84-149`) runs an `UPDATE` that nulls out the plaintext columns:

```sql
UPDATE wims.citizen_reports SET
    witness_pii_blob_enc   = :blob,
    witness_encryption_iv  = :iv,
    witness_crypto_provider = :crypto_provider,
    witness_key_version    = :key_version,
    witness_name           = NULL,
    witness_phone          = NULL,
    device_id              = NULL,
    ip_hash                = NULL
WHERE report_id = :rid
  AND witness_pii_blob_enc IS NULL
```

The object-level authorization boundary for every public civilian endpoint is `_require_device_ownership()` (`src/backend/api/routes/civilian.py:305-326`), which queries the **plaintext** `device_id` column:

```sql
SELECT 1 FROM wims.citizen_reports
WHERE report_id = :rid AND device_id = :device_id
LIMIT 1
```

After encryption runs, the plaintext column is `NULL` and the ownership check never matches. Six of seven public civilian endpoints are 404:

| # | Endpoint | Gate | Currently works? |
|---|---|---|---|
| 1 | `POST /api/civilian/reports` (submit) | rate-limit by `ip_hash` (runs *before* encryption) | Yes |
| 2 | `GET /api/civilian/reports/{id}?device_id=` (track) | `_require_device_ownership` | **No** |
| 3 | `GET /api/civilian/reports?device_id=` (list) | direct `WHERE device_id =` | **No** |
| 4 | `GET /api/civilian/reports/{id}/timeline?device_id=` | `_require_device_ownership` | **No** |
| 5 | `PATCH /api/civilian/reports/{id}/append` | `_require_device_ownership` | **No** |
| 6 | `POST /api/civilian/reports/{id}/followup` | `_require_device_ownership` | **No** |
| 7 | `POST /api/civilian/reports/{id}/notify` (FCM register) | `_require_device_ownership` | **No** |

**The handoff's "page.tsx has no device_id" starting hypothesis was wrong.** The form already correctly calls `getDeviceId()` (`page.tsx:746-754`) and sends the UUID in the payload (`page.tsx:834`); the test suite verifies this (`page.test.tsx:189, 259`). The bug is purely in the backend encryption layer.

**Test gap that allowed the regression:** `src/backend/tests/integration/test_civilian_api.py:225-294` and `:283-294` exercise the ownership check via `_insert_report()` — a direct DB insert helper that bypasses the API and the encryption path. The encrypt-on-submit / ownership-check-on-read round-trip is never tested, so the regression slipped through.

---

## Solution

**Stop treating `device_id` and `ip_hash` as PII that belongs in the encrypted blob.** These are operational primitives:

- `device_id` is a random UUID generated by the user's own browser and stored in their own `localStorage`. It is not personally identifying on its own. It only links to a person if the DB row is combined with the user's localStorage — which is browser-side, not in the DB-compromise threat model.
- `ip_hash` is already a one-way hash of the IP address. It is not personally identifying in the same way a plaintext IP is, and it is used at the rate-limit gate which runs *before* encryption.

`witness_name` and `witness_phone` are real PII. They stay in the encrypted blob and get nulled in plaintext as before.

### The change in one sentence

In `_encrypt_witness_pii()` (`src/backend/api/routes/civilian.py:84-149`): stop putting `device_id` and `ip_hash` into the encrypted blob, and stop nulling them out in plaintext. The function then only handles the two actual-PII columns.

### Threat-model delta vs. PR #448

| Asset | PR #448 | After this fix |
|---|---|---|
| `witness_name` | Encrypted at rest | **Encrypted at rest** (unchanged) |
| `witness_phone` | Encrypted at rest | **Encrypted at rest** (unchanged) |
| `device_id` | Encrypted at rest, plaintext NULL | **Plaintext UUID** (pre-#448 state) |
| `ip_hash` | Encrypted at rest, plaintext NULL | **Plaintext one-way hash** (pre-#448 state) |

A DB compromise post-fix exposes: the same data the system exposed before PR #448. Specifically:
- Random UUIDs (no PII without matching localStorage, which is browser-side).
- One-way IP hashes (no plaintext IP recoverable).

The threat-model loss vs. PR #448 is therefore small and concentrated on the join key (`device_id`) that links rows to a specific browser instance. The privacy export path (`src/backend/api/routes/admin/privacy.py:174`) already reads `device_id` and `ip_hash` from the plaintext columns, so it remains correct without code changes.

### Not Changed

- **DB schema:** no new columns, no new migrations, no dropped columns. The `witness_pii_blob_enc` / `witness_encryption_iv` / `witness_crypto_provider` / `witness_key_version` columns stay (they still hold `witness_name` and `witness_phone`).
- **Encryption infrastructure:** the `SecurityProvider` / `get_crypto_provider()` machinery is untouched. The function still uses the same AAD (`citizen_report:{report_id}`) and the same fail-soft policy.
- **Privacy export code:** `src/backend/api/routes/admin/privacy.py` already reads `device_id` and `ip_hash` from the plaintext columns (line 174). The export code is unchanged by this fix. The export **data** for pre-fix rows (those submitted between 2026-06-23 and the fix deploy) is incomplete — `device_id` and `ip_hash` are NULL in plaintext because PR #448's post-INSERT UPDATE moved them into the blob. See the Follow-up Task section for the data-rescue plan that restores completeness for pre-fix rows.
- **Anonymize path:** `src/backend/api/routes/admin/privacy.py:348-355` already nulls `device_id`, `ip_hash`, and the blob columns. Anonymization semantics are unchanged.
- **Backlog script:** `src/backend/scripts/encrypt_citizen_reports_backlog.py` was a one-time migration run on production. It is not re-run, and its output for already-encrypted rows is not modified by this fix. Old rows have `device_id` and `ip_hash` plaintext NULL (post-backlog) and stay that way.
- **Frontend:** the form already sends `device_id` correctly. No frontend changes.
- **No new dependencies.**

## Test Strategy

Two new integration tests in `src/backend/tests/integration/test_civilian_api.py`, both using the public HTTP API (not `_insert_report`) so the encrypt-on-submit path is exercised:

1. **`test_submit_then_track_returns_report`** — POST a report with `device_id=<uuid>`, then GET `/api/civilian/reports/{report_id}?device_id=<uuid>`. Assert 200 and the report body matches. This is the user-visible flow from the bug report.

2. **`test_submit_then_list_includes_report`** — POST a report with `device_id=<uuid>`, then GET `/api/civilian/reports?device_id=<uuid>`. Assert 200 and the response contains the just-submitted `report_id`. This covers the "list my reports" path that also uses the plaintext `device_id` column.

Both tests must run against a backend where the encryption provider is active (the default test environment), so the encrypt-on-submit path is exercised. The existing test for the privacy export (`test_privacy.py::test_export_report_decrypts_pii`) is the canary that the blob still works for `witness_name` and `witness_phone` — no changes needed there.

## Test Helper Foot-Gun: `_insert_report()`

**This is a hard rule for the implementer.** The helper at `src/backend/tests/integration/test_civilian_api.py:92` is the reason the PR #448 regression slipped through CI. It writes a row directly to `wims.citizen_reports` via SQLAlchemy — bypassing the FastAPI route, the rate-limit gate, AND the `_encrypt_witness_pii()` post-INSERT update. Any test that uses it to set up a parent report and then exercises an ownership-gated endpoint (track, append, followup, notify, list) is silently *not testing the production code path*. That is exactly how PR #448's `device_id = NULL` UPDATE went undetected.

### Action — rename and warn

1. **Rename `_insert_report()` to `_insert_report_raw_bypassing_encryption()`** at the definition site (`test_civilian_api.py:92`). The new name is intentionally verbose: every call site will read as "I am knowingly bypassing the encryption layer." A shorter alternative (e.g. `_insert_report_pre_encryption_state()`) is acceptable if the implementer prefers, but the name MUST contain "bypassing" or "raw" or "pre_encryption" so the foot-gun is self-documenting at the call site.
2. **Update all 30 call sites** in the same file to the new name. Mechanical rename, no logic changes.
3. **Add a module-level docstring** to the helper that reads, in full:
    ```
    WARNING — this helper inserts rows directly into wims.citizen_reports via
    SQLAlchemy, bypassing the FastAPI route, the rate-limit gate, and the
    _encrypt_witness_pii() post-INSERT update. It is suitable for setting up
    state in tests that do NOT exercise the encrypt-on-submit / ownership-check
    round-trip (e.g. status transitions, queue ordering, triage logic).

    For tests that exercise the submit-then-track / submit-then-append /
    submit-then-notify flows, you MUST go through the public HTTP API
    (client.post('/api/civilian/reports', ...)) so the real encrypt-on-submit
    path runs. Using this helper for those tests will silently hide any
    regression in the encryption layer — which is exactly how the
    PR #448 device_id regression slipped through.
    ```
4. **The two new tests added by this fix (`test_submit_then_track_returns_report`, `test_submit_then_list_includes_report`) must use the public HTTP API** (already specified above). They MUST NOT call the renamed helper.

### Why this matters going forward

A future agent who sees `_insert_report(db_session, device_id=...)` at a call site and thinks "great, this is how you set up a parent for the ownership test" will reproduce the same blind spot. The rename + docstring turn the foot-gun into a self-documenting warning. It does not eliminate the helper (some tests legitimately need raw state — status-only tests, queue-ordering tests, FK setup) — it makes the cost of using it for ownership tests visible.

## Scope and Constraints

- **In scope:** restore the six ownership-gated public endpoints to working state. Keep `witness_name` and `witness_phone` encrypted at rest.
- **Out of scope:** migrating existing rows. Per the handoff constraint, rows created before this fix (including report #540) stay as-is — their `device_id` plaintext is `NULL` and the ownership check will still 404 for them. Only new submissions get a working `device_id`.
- **Out of scope:** re-encrypting the historical backlog. The backlog script's output is not modified; it stays as a one-time migration of pre-fix rows.
- **Out of scope:** changing the rate-limit semantics. Rate limiting still uses `ip_hash`, which now stays plaintext (it was plaintext before PR #448 too).
- **Out of scope:** the `fire_incidents.ai_narrative` encryption from PR #448. That path has no ownership check; it is unaffected by this fix and needs no change.

## Follow-up Task: Privacy Export Data-Rescue for Pre-Fix Rows

**This is a known gap, explicitly accepted for this fix, and tracked as a follow-up.** It is not blocking, but it is real.

### The gap

The privacy export path at `src/backend/api/routes/admin/privacy.py:174` reads `device_id` and `ip_hash` from the **plaintext** columns:

```sql
SELECT report_id, witness_name, witness_phone, ip_hash, device_id, ...
```

For any row that was submitted between 2026-06-23 (PR #448 merge) and the deploy of this fix, the plaintext `device_id` and `ip_hash` columns are `NULL` — the values were moved into the encrypted blob by the post-INSERT UPDATE that this fix is removing. A data-subject exercising their RA 10173 export right on a pre-fix row will receive `device_id: null` and `ip_hash: null` in the export, even though those values exist encrypted in `witness_pii_blob_enc` for the same row. The `witness_name` and `witness_phone` fields are NOT affected — they are correctly decrypted from the blob during export.

This is a privacy completeness regression: a user has a right to receive all data the controller holds about them, and the export currently under-reports for pre-fix rows. It is a compliance bug, not a security bug — the data is still in the database, just not surfaced in the export.

### Follow-up: one-time data-rescue script

**File to add later (NOT in this fix):** `src/backend/scripts/restore_citizen_reports_device_id_backlog.py`

**Behavior:**
1. Select rows where `device_id IS NULL` AND `witness_pii_blob_enc IS NOT NULL` (i.e. rows that were encrypted by PR #448 or the existing `encrypt_citizen_reports_backlog.py` script).
2. For each row, decrypt `witness_pii_blob_enc` using the same AAD (`citizen_report:{report_id}`) and the same `get_crypto_provider()` machinery the production code uses.
3. If the decrypted JSON contains a `device_id` key, write it back to the plaintext `device_id` column. Same for `ip_hash`.
4. Leave `witness_name`, `witness_phone`, and the blob columns (`witness_pii_blob_enc`, `witness_encryption_iv`, `witness_crypto_provider`, `witness_key_version`) UNCHANGED — those are still correct post-#448. The script only restores the two operational-primitive columns that this fix stops putting in the blob.
5. Idempotent: rows where `device_id IS NOT NULL` are skipped.
6. Audit-logged: each row touched is recorded in `security_audit_trails` with action `CIVILIAN_REPORT_PII_RESCUE` so the RA 10173 audit trail is intact.
7. Dry-run flag (`--dry-run`) that prints the count of rows that would be updated without writing.

**When to run it:** After this fix is deployed and confirmed working on production. Not before — running it before the fix lands would write plaintext `device_id` to rows that the current code will then re-encrypt to NULL on the next `_encrypt_witness_pii()` no-op (the `WHERE witness_pii_blob_enc IS NULL` clause prevents the loop, but the ordering matters for clarity).

**Test:** a new test in `src/backend/tests/test_privacy.py` (or a dedicated `test_restore_citizen_reports_device_id_backlog.py`) that creates a row, encrypts it via the PR-#448 path, runs the script in a transaction, and asserts the plaintext columns are restored AND the blob columns are untouched.

**Tracking:** add a TODO in `system-wiki/log.md` under a new "Follow-up" section pointing to this spec section, and a corresponding task in the project issue tracker (`x1n4te/WIMS-BFP-PROTOTYPE` via `gh issue create`).

**Why this is not blocking the current fix:** the bug reported by the user (report #540, the tracking page 404) is a functional blocker for the new-submission flow. The privacy-export gap for pre-fix rows is a compliance issue that already exists in production today (since PR #448 landed) and is not made worse by this fix. Both should be tracked, but only one blocks the user's reported workflow.
